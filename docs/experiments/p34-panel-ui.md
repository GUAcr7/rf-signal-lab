# P34：屏幕自绘 UI —— 面板渲染器与三调制实测图

- 日期：2026-10-20 晚（北京时间）。
- 背景：任务①"屏幕上显示频谱/星座"一直是完全空白 —— 显示模式下只显示厂家 XFCE 桌面，没有任何本项目的东西。
- **本轮产出：一个可用的面板渲染器 + 三种调制的真实数据实测图。尚未上板显示。**
- 范围：纯主机侧渲染。未操作板卡、未改位流、未动 FPGA 工程。

## 1. 设计取舍

**渲染在主机做，板上只写字节。** 理由：

| 方案 | 问题 |
|---|---|
| 板上画 | 新板根文件系统没有 Python / 绘图库；要造一套 C 绘制 |
| 主机渲染 + 传字节 | 板上只需 `base64 -d \| gunzip > /dev/fb0`；版面可在电脑上审阅与回归 |

代价：这不是"实时刷新"，是**一帧快照**。要做到实时，必须等合并位流（RF 与显示共存）以后，由板上程序持续刷新。本轮不声称实时。

板的工具已验证存在：`/bin/gunzip`、`/bin/gzip`、`/bin/base64`、`/bin/dd`。

## 3. 实测结果

用 `p24-rx-*-decoded/segment.bin`（2026-10-18 冷启动的三段单缓冲真实采集）渲染：

| 调制 | EVM | 正交抑制 | 幅度 CV | fb 字节 | gzip |
|---|---:|---:|---:|---:|---:|
| BPSK | **−37.18 dB** | +45.27 dB | 0.0127 | 1,536,000 | **22,262 B** |
| QPSK | **−37.07 dB** | −0.02 dB | 0.0083 | 1,536,000 | **21,725 B** |
| 16QAM | **−37.04 dB** | −0.12 dB | 0.3447 | 1,536,000 | **22,423 B** |

EVM 与 [EXP-HW-016](exp-hw-016-cold-start-reproduction.md) 记录的 −37.18 / −37.07 / −37.04 **完全一致**，说明面板显示的星座来自同一套已验证的解调，不是另画一条路径。

**gzip 后仅 ~22 KB** —— 串口传输约 3 秒，这是本方案最关键的实际优势（原始 1.5 MB 需要约 3 分钟）。

产物：`results/p34-panel-{bpsk,qpsk,qam16}-v4/{panel.png,panel.fb,panel.fb.gz,report.json}`。

## 4. 修掉的两个显示错误（都是自己发现并改正的）

### 4.1 16QAM 星座画成了圆环

第一版 CLI 对所有调制都用 M 次方相位对齐。BPSK/QPSK 是恒模，这方法有效；**16QAM 不是恒模**，`unit⁴` 不塌缩，星座被留在任意角度，画出来是一圈**同心弧**，EVM 只有 −14.96 dB。

这正是 [EXP-HW-015](exp-hw-015-qam16-difference-check.md) 已经确立的结论，我在新 CLI 里又犯了一次。

**修法**：按调制分开 —— PSK 用 M 次方（并减去星座自身参考相位），16QAM 先 `track_carrier` 再 `align_rotation`。修后 16QAM 显示为正确的 **4×4 网格**，EVM −37.04 dB。

**教训：面板会把解调错误放大成肉眼可见的错误图形，这是好事 —— 但它绝不能拿来展示未经验证的解调路径。**

### 4.2 频谱跨满 30.72 MHz，把信号压成一根针

240 kHz 带宽的信号放在 ±15.36 MHz 里几乎看不见。

**修法**：默认绕**载波**缩放到 ±2 MHz，并把横轴标成"相对载波"。注意是绕**载波**而不是绕 PSD 峰 —— 绕峰会因为杂散线导致轴范围不对称（实测出现过 −0.990…+2.970 MHz）。

## U1. 帧缓冲实测参数

| 项 | 实测 |
|---|---|
| `/dev/fb0` | 字符设备，root:video |
| `bits_per_pixel` | **32** |
| `virtual_size` | **800,480** |
| `stride` | **3200** = 800×4 ✓ |
| `wc -c < /dev/fb0` | **3,072,000** = 两页 |

**双缓冲/两页**这点很关键：帧缓冲可读长度是画面大小的两倍，所以对**整设备**做哈希永远不可能与单帧文件相等。正确做法是只比第一页：

```sh
dd if=/dev/fb0 bs=1024 count=1500 | sha256sum    # 1500*1024 = 1,536,000
```

## U3. 一个真实故障：帧缓冲控制台会重绘覆盖画面

**现象**：第一次写完测试图后画面正常，但几分钟后图像被破坏（哈希从 `a6e4301a…` 变成 `c026d4f8…`）。

**根因**：`/sys/class/vtconsole/vtcon1` 是帧缓冲控制台，**内核与串口输出会被镜像画到面板上**。我第一次执行 `echo 0 > vtcon1/bind` 后**没有读回确认**，实际 `bind` 仍是 **1**。

**判据**：解绑成功时内核会打印
```
Console: switching to colour dummy device 80x30
```
并且 `cat vtcon1/bind` 必须读回 **0**。

**验证方法**（重要）：解绑后写入画面，再**故意连发几条会产生控制台输出的命令**，然后回读第一页哈希：

```
写完后        a6e4301a…  ✓
发两条 echo 后 a6e4301a…  ✓ 未变
```

**这条"发流量再验哈希"的方法才是真验证**，只比一次哈希证明不了抗覆盖。

**所以画面消失不是"点屏幕"造成的** —— 当时没有 X、没有程序读触摸、也没有进程写 `/dev/fb0`；是控制台重绘。

## U4. 持久化与切换

板端现在有：

| 路径 | 内容 |
|---|---|
| `/root/panels/{qpsk,qam16}.fb.gz` | 21,725 / 22,423 B，**SD 卡持久**（断电不丢） |
| `/root/show-panel.sh` | 切换脚本：先解绑 vtcon1 并校验 `bind=0`，再写入 |

用法：`/root/show-panel.sh qpsk` 或 `/root/show-panel.sh qam16`。

两次切换的实测哈希均与渲染文件一致，且脚本未打印解绑告警。

**注意**：`/tmp` 下的临时副本在重启后消失，但 `/root/panels` 里的不会；`vtcon1` 的绑定状态重启后也会恢复为 1，所以**必须用脚本**而不是手工重定向。
