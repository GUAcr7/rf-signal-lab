# EXP-HW-011：双板射频链路打通 + 实测线性上限

- 日期：2026-10-17 深夜。
- 承接 [EXP-HW-010](exp-hw-010-old-board-recovery.md)（旧板恢复）与 [EXP-HW-009](exp-hw-009-new-board-iq-capture.md)（新板采集）。
- 本轮目标：`EXP-ERRATA-20261017` §9 最后一项 —— **双板实际连接**，并按降幅流程找出可用的幅度上限。
- **结果：链路打通；实测判定压缩始于 256→512 档；256 档及以下线性。**
- 本轮性质：**真实双板、真实射频、真实发射**（旧板 4 次成功发射，每次 30 s）。

## 1. 结论先说

| 问题 | 答案 |
|---|---|
| 两块板能否直连？（不接衰减器） | **能。** 64 档起步即可收到清晰单音，未削顶 |
| 能开到多大幅度？ | **256 档及以下线性**；512 档开始压缩 |
| 是 ADC 削顶吗？ | **不是。** 全程 `endpoint=0`，峰值最高 823（满量程 2048） |
| 所以压缩在哪？ | **模拟链路**（TX 或 RX 的 RF 前端）。本实验无法区分是哪一侧 |

这正面回答了此前"不需要衰减器"那次误判真正该回答的问题：**不是"会不会烧坏"，而是"到哪个幅度就不线性了"。**

## 3. 实测数据

### 3.1 基线（不发射）

| 项 | 值 |
|---|---|
| 平均功率 | 227.0 |
| rms | 15.07 |
| 峰均比 | **6.30 dB** |
| 原始字范围 | −284 … 277 |
| 端点比例 | 0.0 |

峰均比 6.3 dB 是噪声的特征。

### 3.2 四档发射（每档 30 s，窗口内采集）

| 档位 | 平均功率 | rms | 峰均比 | 峰值 | 端点 | 相对满量程 | 步进增益 | 判定 |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| **64** | 13,243.2 | 115.08 | **1.59 dB** | 138 | 0.0 | −25.0 dBFS | — | — |
| **128** | 51,353.0 | 226.61 | 0.82 dB | 249 | 0.0 | −19.1 dBFS | **+5.886 dB** | 线性 |
| **256** | 192,362.3 | 438.59 | 0.50 dB | 464 | 0.0 | −13.4 dBFS | **+5.736 dB** | 线性 |
| **512** | 636,867.9 | 798.04 | 0.26 dB | 823 | 0.0 | −8.2 dBFS | **+5.199 dB** | **压缩** |

预期每次 **+6.0206 dB**（幅度加倍 → 功率 ×4）。

### 3.3 判据与判定

```
step 0: 13243.2 -> 51353.0   +5.886 dB   error -0.135   linear
step 1: 51353.0 -> 192362.3  +5.736 dB   error -0.285   linear
step 2: 192362.3 -> 636867.9 +5.199 dB   error -0.821   compressing

verdict: NON-LINEAR (first non-linear step 2)
```

**误差单调增大（−0.135 → −0.285 → −0.821）**，正是从线性区滑向压缩区的典型形状，不是随机噪声。

### 3.4 为什么判定不是"ADC 削顶"

| 证据 | 读数 |
|---|---|
| 端点比例（满量程 2048） | **四档全为 0.0** |
| 最高峰值 | 823，**仅为满量程的 40%** |
| 峰均比 | 单调下降 1.59 → 0.26 dB |

如果 ADC 削顶，会看到端点堆积、峰值贴住 2048、峰均比反而回升。**都没有。** 所以压缩发生在 ADC 之前（RF/IF 模拟链路）。

**但本实验无法区分是 TX 侧还是 RX 侧** —— 需要频谱仪旁路观察才能定。

## 5. 本轮踩到的三个操作故障（都有价值）

### 5.1 旧板中途重启，`/tmp` 全清、`boot_id` 变了

旧板根文件系统是 `none on / type rootfs (rw)`，**`size 0`，全是内存**。断电/重启后一切文件消失。

第一次发射失败报 `can't cd to .../stage: No such file or directory`，原因是板子在约 7 分钟前重启过（很可能插射频线时碰到电源）：

| 项 | 重启前 | 重启后 |
|---|---|---|
| `boot_id` | `ea863ecc-…` | `f2c4a78e-…` |
| `/tmp` | 有恢复包 | **空** |

**后果**：`boot_id` 是发射守卫的身份，用旧值会被拒。**每次重启都必须重新读 `boot_id` 并重传文件。**

### 5.2 用错波形哈希，被守卫拦下（这是好事）

128 档第一次我用成了 **256 档的 sha256**（`fa20e4b5…`）。程序校验文件哈希 → 不符 → **退出 2，未发射**。

**这正是守卫该有的行为**：它不信任调用者给的"这是哪支波形"，自己算。若没有这层校验，我会拿 256 的数据当 128 的结果，把步进算成 0 dB。

### 5.3 两个任务抢 COM9，512 档压根没发出去

我启动 512 档发射时，256 档的任务还占着串口：

```
对端口"COM9"的访问被拒绝。
```

于是那次采到的是**基线噪声**（功率 240.8，与基线 227 相当）。**如果我只看数字不看出处，会误判成"512 档功率反而下降"。** 重发后得到 636,867.9。

**教训**：串口是独占资源，并发任务必须串行化并确认上一个已释放。

## 6. 同时修正的工具缺陷

`experiments/p16_check_saturation.py` 原先按 **2 通道**解析，而实测数据是 **4 通道**（I1,Q1,I2,Q2）。这正是 [EXP-HW-009](exp-hw-009-new-board-iq-capture.md) 记录的陷阱，却在自己的工具里又犯了一次。

修复：

| 项 | 修正 |
|---|---|
| 解析 | 改用 `decode_iq_dma_s16()`，增加 `--channels`（默认 **4**）、`--i-index`、`--q-index` |
| fixture | `p16_make_saturation_fixtures.py` 改为写 **4 通道**，与真机一致 |
| 自测 | 4 通道 fixture 重跑，线性仍判 LINEAR、压缩仍判 NON-LINEAR |

**自测与实测互相印证**：

| 来源 | 三步增益 |
|---|---|
| 合成压缩 fixture | +5.937 / +5.705 / **+4.895** dB |
| **真实双板链路** | +5.886 / +5.736 / **+5.199** dB |

两组形状高度一致，说明工具在真机上行为可预期。

## 9. 对项目决策的影响

1. **双板直连可行，无需衰减器** —— 但这句话现在有实测依据，且附带明确的幅度上限：**≤256 档（RX 手动 0 dB）**。
2. **降幅流程必须保留** —— 512 档确实压缩，若一上来就用 512，得到的 IQ 是失真的，后续所有调制识别结论都会被污染。
3. **接收调制信号前，必须先确认工作点在线性区** —— 下一步用 256 档发 BPSK/QPSK/16QAM，并复查步进是否仍为 +6.02 dB。
